# PICADS authoring languages and design-file contract

**Applies to PICADS v0.16.8 r9d (source snapshot).** This is a reference for **PICADS projects in general**, not documentation for any particular example processor. The file extensions represent *different stages and responsibilities*, not alternative spellings of the same hardware design. This guide describes behavior confirmed from the PICADS source and existing example projects; an installed toolchain/PDK is still needed for actual RTL-to-GDS.

> **Most important distinction:** PICADS's typed Python/C frontend creates a DLS logic design and generated Verilog. Separately, `architecture.co` can select **hand-authored Verilog RTL macros** and instruct LibreLane to harden and place those macros. PICADS r9d **does not automatically partition a general Python CPU class into these macros, and does not prove that the independently written Python and RTL represent the same circuit.**

## 1. Which language/file should I use?

| File / language | Edited by | Purpose in PICADS | What PICADS actually does |
|---|---|---|---|
| `chip.yaml` (YAML) | Project author | Manifest: source, MCD, CO, tools, verification and physical backend | Loads project and validates supported keys; starts requested stages |
| `circuit.py` (restricted, typed Python) | Logic designer | Describe arithmetic, combinational logic and supported clocked/transactional hardware | Compiles **supported** functions to gate-level DLS and structural Verilog; **does not** synthesize arbitrary Python programs/classes |
| `.c`, `.cpp`, `.cc`, `.cxx` (restricted C-compatible syntax) | Logic designer | Alternative to typed Python for fixed-width scalar functions | Translates supported C AST into the same typed Python intermediate, then DLS/Verilog; **not** full C/C++ or LLVM |
| `design.mcd` (YAML, *Module and Chip Description*) | Architect | Choose top function, bind named functional modules, declare requirements/explicit networks | Validates declared functions, module requirements and supported network connections; names alone do not fence cells physically |
| `architecture.co` (YAML, *Chip Orchestration*) | Architect / physical designer | Choose arithmetic strategy, schedule, resource limits, floorplan policy and hard RTL macros | Applies **only implemented** directives; certain physical constraints are backend-enforced and others are merely guides |
| `rtl/*.v` (Verilog HDL) | RTL designer | Explicit logic and hierarchy for independently hardened standard-cell macros and their top assembly | If selected by `physical_macros`, sends RTL to Yosys/LibreLane for hardening and top-level routing; **not** parsed by the Python source frontend |
| Generated `*.dls` (JSON) | Compiler | Actual primitive-gate and state graph, simulation, provenance | Generated by PICADS; usually inspect, do not hand-edit |
| Generated `*.v` (Verilog) | Compiler | RTL export of DLS generated from Python/C | Used by synthesis in the regular non-macro flow; not automatically substituted for independent CO macro RTL |
| Generated `*.aig` (AIGER) | Tool | ABC/AIG experimental graph inspection | Independent optimization artifact; **not** necessarily the PDK-mapped netlist used to route the chip |
| Generated `.lef`, `.def`, `.gds` | Physical tools | Macro abstraction, placed/routed design database, final mask geometry | Output artifacts; GDS generation does **not** certify fabrication signoff |
| `.lyp` | KLayout | Visible layer display/style mapping | Controls viewer visibility, not fabrication geometry |
| Testbench `.v`, test `.py`, `.hex` | Validation/test author | Independent simulation or firmware inputs | Requires the corresponding simulator/assembler; these are **not** automatically synthesized merely by being in the project folder |

## 2. Minimal four-file logic project

The normal PICADS project root may start with exactly these four files:

`chip.yaml`:

```yaml
name: SmallLogic
source: circuit.py
mcd: design.mcd
co: architecture.co
physical:
  enabled: false  # enable and configure a real PDK/toolchain before layout
```

`design.mcd`:

```yaml
top: calculate
modules:
  - name: Calculator
    function: calculate
    purpose: Adds two 8-bit values and returns an 8-bit result
```

`architecture.co`:

```yaml
architecture:
  adder: ripple
schedule:
  mode: spatial
```

`circuit.py`:

```python
def calculate(a: u8, b: u8) -> u8:
    return a + b
```

The `u8` names belong to **PICADS's hardware annotation vocabulary**; they are not normal built-in Python types. `calculate` must match MCD's top and its `function:` binding. PICADS applies bitvector return-width rules: an addition may have an intermediate widened result before the declared `u8` output truncation.

Compile: `python -m chipcompiler compile PATH_TO_PROJECT` (with PICADS installed or `PYTHONPATH=src` from the repo root). Outputs are in the project's `build/latest/` folder. If changing only `circuit.py`, regenerate DLS/Verilog; if changing CO physical positions, regenerate the **physical layout** as well.

### What the typed Python frontend accepts

- Typed `def` functions with supported `uN`, `sN`, `bool` annotations (simple spatial functions support widths up to 4096 bits; individual scheduler modes impose tighter limits).
- Constants; fixed-size local values; bitwise operations; arithmetic; comparisons; conditional branches and expressions; literal-bounded `for range(...)`; supported pure helper calls.
- Synchronous registers using `reg('unique_name', value, init=..., enable=..., reset=...)`, with **synchronous reset** taking precedence over enable.
- For **transactional** mode, supported `mem_read` and `mem_write` primitives against a fixed register-bank memory specified by CO, plus START/READY/DONE/STALL/RESET/FAULT protocol. This is not general Python RAM syntax.

**Not accepted as hardware merely because Python executes it:** ordinary object/class instances, list-backed memories, Python imports, arbitrary `while` loops, dynamic allocation, file I/O, dynamic shifts, decorators, Python threads, and unbounded iteration. A full executable Python CPU *simulator* can coexist beside a hardware-eligible function, but only the supported source top selected by MCD is compiled. Consult `docs/LANGUAGES.md` and `docs/TRANSACTIONAL_SCHEDULER_v0.7.0.md` for mode-specific restrictions.

**Bit widths are significant:** PICADS uses explicit hardware bitvector rules; e.g. addition may widen by one bit and multiplication by combined operand widths. The returned `uN`/`sN` annotation limits the output width. Do not assume ordinary unlimited-precision Python arithmetic.

## 3. C and C-compatible C++ as alternative behavioral sources

Set `chip.yaml` `source: circuit.c` or `source: circuit.cpp` and retain the MCD/CO files. Example:

```c
#include <stdint.h>
uint8_t calculate(uint8_t a, uint8_t b) {
    return a + b;
}
```

This accepts only a restricted, fixed-width, value-oriented **C AST** through `pycparser`; `.cpp`, `.cc`, `.cxx` accept **C-compatible** constructs, not C++ classes, templates, references, exceptions, overloaded operators, libraries or STL. Typical supported syntax: `uint8_t/16_t/32_t/64_t`, signed equivalents, `bool`, initialized local scalars, direct pure function calls, `if`, `?:`, comparisons, bitwise/arithmetic operators, and **literal-bounded** `for` loops. No pointers, arrays, structs, casts, heap, `while`, macros or arbitrary preprocessor headers; the only explicitly recognized includes are `stdint.h` and `stdbool.h`.

C is normalized to PICADS bitvector semantics rather than fully preserving ISO C integer promotions and undefined-behavior rules. Inspect `build/latest/normalized_source.py`; optional `verification.native_c: true` requests bounded independent native GCC/G++ comparison when present. Do **not** use this frontend for firmware running *on* a processor: this is a **hardware description input**, not a cross-compiler to a CPU ISA.

## 4. MCD: functional boundaries and explicit networks

`design.mcd` identifies the hardware top and connects it to source functions:

```yaml
top: calculate
modules:
  - name: CalculationUnit
    function: calculate
```

A `modules[].name` is a declared name; `function` is a checked binding to an existing source function. An unbound descriptive name does **not** magically create gates. For actual logical module networks, MCD's `network.instances`/`network.outputs` supports explicit compatible function instances, wiring and a limited `auto_connect: unique_width` heuristic. Those module instances can create **logical** DLS hierarchy; they are not automatically a physical-fenced macro arrangement. Read `docs/MCD_NETWORK_v0.6.0.md` for supported fields and limitations.

MCD source helper-hierarchy behavior also depends on CO `modules.hierarchy`; an explicit MCD network preserves instance hierarchy under its documented rules. MCD does not describe silicon layer stacks or transistor mask geometry.

## 5. CO: synthesis, scheduling and placement constraints

CO is YAML, **not executable Python**. Its implemented top-level keys in this release include:

| CO directive | Main job | Key limits |
|---|---|---|
| `architecture.adder` | Choose `auto`, `ripple`, `prefix` for supported generated adders | Applies only where generator implements strategy |
| `allocation.sharing`, `max_instances` | Supported source operator sharing / resource limits | Not an arbitrary global silicon resource optimizer |
| `schedule.mode` | Select `spatial`, `time_share`, `transactional`, specialized fabric modes | Each mode has its own supported source constructs |
| `memory.depth`, `data_width` | Fixed memory for supported scheduled flow | Not a magic SRAM macro generator |
| `modules` | Logical hierarchy/naming controls | Not hard macro placement itself |
| `floorplan` | Logical module guides/validation and required hard **placement** keepouts | `guide` ≠ physical macro fences; `FP_OBSTRUCTIONS` doesn't ban all routing |
| `synthesis.abc_aig` | Create AIGER optimization/inspection artifacts | Independent of final PDK mapped placement netlist |
| `physical_macros` | Explicitly harden and place Verilog macro blocks | Requires supported top RTL with matching instances and a real physical toolchain |

**Physical macro CO example (illustrative):**

```yaml
physical_macros:
  enabled: true
  enforcement: required
  top_module: top_chip
  top_rtl: rtl/top_chip.v
  halo_um: 5
  placement:
    mode: compact               # compact | row | manual
    region_um: [20, 20, 420, 420]
    stayouts_um:
      - [190, 190, 220, 225]
  spacing:
    min_um: 12
    preferred_um: 20
    max_um: 60
  blocks:
    - name: ProcessingBlock
      module: processing_block
      instance: u_processing
      rtl: rtl/processing_block.v
      clock_port: clk
      die_size_um: [100, 100]
    - name: StorageBlock
      module: storage_block
      instance: u_storage
      rtl: rtl/storage_block.v
      clock_port: clk
      die_size_um: [120, 120]
```

This is not a complete runnable project by itself: matching module declarations and instances must exist in the Verilog files, a suitable `chip.yaml` physical configuration must exist, and actual hardened sizes may differ from `die_size_um` hints. Two to 32 **unique module types** are supported by the r9 backend. `top_rtl` must instantiate exactly the named required blocks. `compact` uses deterministic 2-D packing (not a proof of minimum wire length); `manual` requires every block's `location_um: [x,y]`. The GUI **Physical / Masks → Edit CO Floorplan (Drag and Drop)** writes manual positions back to CO.

**Placement region and stay-outs:** `region_um` is the allowed macro bounding rectangle, while `stayouts_um` denotes forbidden areas for **macro placement**. `floorplan.keepouts` with `kind: hard` and `enforcement: required` also apply as placement exclusions. Required spacing/halo must still fit. Neither kind of stay-out automatically prevents **wires, power straps or vias** from crossing upper metal above the area. See `docs/CO_DRAG_DROP_STAYOUTS_r9d.md` and `docs/CO_NATIVE_HARD_MACROS_r9.md`.

**Distinguish `required` carefully:** In guide-floorplan modules, `required: true` means a logical module selector must be present; `enforcement: required` for a **generic flattened logic module fence** is not supported and fails closed. For the native `physical_macros` backend, `enforcement: required` applies to actual separately hardened, named RTL macros with post-layout instance checks. These are different mechanisms.

## 6. Verilog: when it is the physical design source

PICADS r9d's *top-level source selection* (`chip.yaml: source`) does **not** accept `.v` as its normal Python/C compiler entrypoint. Instead, CO `physical_macros.top_rtl` and `blocks[].rtl` explicitly select Verilog modules for an **independent physical macro flow**:

1. RTL child modules must have named ports and fully defined sequential/combinational behavior.
2. The top RTL must instantiate the required modules under the **exact** CO `instance` identifiers.
3. When **Generate Physical Layout** runs, PICADS hardens each RTL child to GDS/LEF/netlist views, then integrates and routes them at the top level.
4. PICADS checks final DEF coordinates and GDS hierarchy for all required macro instances before declaring `MACRO_GDS_AND_DEF_PLACEMENT_VERIFIED`.
5. **Verify Existing Layout** performs deferred child and parent checks. A generated GDS is not itself signoff.

PICADS **does not automatically prove** the Verilog macro implementation equals the `circuit.py` compiler reference. This matters for CPU examples: a full Python interpreter/simulator *by itself* doesn't mean its logic is what LibreLane manufactures. Functional RTL verification needs separate simulation/formal tests and a verified model/port/clock correspondence.

## 7. Project manifest: physical configuration and tools

Example fragment in `chip.yaml` (values are illustrative, not a universal recipe):

```yaml
name: ExamplePhysicalProject
source: circuit.py
mcd: design.mcd
co: architecture.co
tools:
  execution: wsl
  wsl_distribution: Ubuntu
verification:
  external_rtl: false
physical:
  enabled: true
  pdk: sky130A
  std_cell_library: sky130_fd_sc_hd
  clock_period_ns: 100
  core_utilization: 25
  timeout_s: 14400
  power_grid:
    rail: true
    global_connections: true
    multilayer: true
    connect_macros: true
    core_ring: false
```

The PDK/std-cell configuration is essential: `sky130A` + `sky130_fd_sc_hd` is a real example target, **not** a general-purpose material abstraction, thin-film transistor recipe or foundry qualification. When using Windows + Ubuntu WSL backend, start **Docker Desktop**, wait for engine readiness, enable *Settings → Resources → WSL Integration → Ubuntu*, and keep Docker running throughout the LibreLane step. A Docker preflight failure is not a logic error.

## 8. What the commands/buttons do

| CLI / GUI action | Main inputs | Output or effect |
|---|---|---|
| `picads init PROJECT` | Directory | Creates four simple project files **only when missing** |
| `picads compile PROJECT` | `chip.yaml` + source + MCD/CO | Generates DLS/structural Verilog, architecture and diagnostic files |
| `picads simulate PROJECT --inputs '{"a":1,"b":2}'` | DLS-compatible inputs | Runs DLS simulation (mode-dependent protocol semantics) |
| `picads build PROJECT` | Generated RTL + external Yosys | Attempts synthesis with installed tools |
| `picads physical-preflight PROJECT` | Physical/tool settings | Checks readiness; does not create a GDS |
| `picads layout PROJECT` / **Generate Physical Layout** | Regular RTL or CO-selected macro RTL + PDK + LibreLane | Stops at generated GDS stage and records **unverified** status |
| `picads verify_layout PROJECT` / **Verify Existing Layout** | Existing routed layout, saved hashes/cache | Attempts deferred verification; do not confuse with generation |
| `picads physical PROJECT` | Same + physical tools | Legacy one-shot complete physical flow |
| `picads gui PROJECT` | Project | Opens desktop GUI; includes CO placement editor |
| `picads doctor` / `picads dependencies wsl-status` | Tool environment | Detects optional tools and WSL backend |
| `picads diagnose PROJECT` | Build/logs | Produces diagnostic archive; source inclusion optional |

Installed package entry points are `picads` and `chipcompiler`; `python -m chipcompiler` also works in an appropriate environment. For Windows, PICADS includes `RUN_GUI.bat`, `SETUP_GUI_WINDOWS.bat`, tool diagnostics and setup scripts. The GUI is optional; the compiler can compile simple projects without Docker, Linux or physical EDA tools.

## 9. Generated artifacts: how to read them

- `build/latest/<top>.dls`: versioned graph of primitive gates, input/output buses, internal wires and registers; helpful for checking **what Python/C compilation actually produced**.
- `build/latest/<top>.v`: structural Verilog of that generated DLS (not automatically the hand-written hard-macro top RTL).
- `build/latest/architecture.json`, `co_schedule.json`, `report.json`, `events.jsonl`: architecture/schedule/status/evidence; inspect them **before** claiming a build is correct.
- `build/latest/normalized_source.py`: C/C++ subset normalized to the Python frontend, when applicable.
- `build/latest/co_macros/co_macro_plan.json`: the **requested** macro arrangement, not proof of final placement.
- `build/latest/co_macros/co_macro_placement_verified.json`: post-run evidence of required macro instances in DEF and GDS.
- `build/latest/runs/<run_tag>/final/gds/<top>.gds`: actual GDS generated by LibreLane (when successful).
- `build/latest/klayout_layers_picads_exact.lyp`: a display-only viewer palette mapping actual observed GDS layer/datatype pairs. Showing/hiding its layers does **not** change the GDS.
- `build/co_macro_cache/`: expensive reusable hardened macros; source edits or config/PDK changes can invalidate them. Do not delete casually.

Status vocabulary: **PASS** = that individual check passed; **PARTIAL/UNAVAILABLE/UNVERIFIED/DEFERRED** = an important check is missing or not run; **LAYOUT_GENERATED_UNVERIFIED** = GDS exists, but physical signoff is not proven; **FAILED** = a tool or requested hard constraint failed. No combination of successful local Python tests alone constitutes foundry signoff.

## 10. Common mistakes

1. **Writing a Python CPU class and expecting it to appear in the GDS.** The main Python compiler handles a restricted typed function/subset. If CO selects independent hard RTL macros, *that RTL* is the physically built logic.
2. **Using MCD module names as physical walls.** Logical naming and placement fencing are different; use the native `physical_macros` mechanism for explicit RTL module separation.
3. **Treating `.co` as executable code.** It is declarative YAML interpreted only where PICADS has an implementation; unsupported keys can be reported but do not implement novel constraints.
4. **Mistaking a GDS preview or layer label for silicon verification.** KLayout visualization is not DRC/LVS/timing/PDN closure.
5. **Closing Docker Desktop between physical runs.** WSL Docker integration must remain available while LibreLane operates.
6. **Forgetting to regenerate after editing coordinates.** Saving CO positions does not move an already routed DEF/GDS.
7. **Confusing firmware C/assembly with PICADS's hardware C subset.** PICADS's C frontend creates hardware; it does not assemble machine code for a CPU instruction set.
